\section*{Executive findings}
The implemented Solidity wallet verifies three experimental signature profiles
directly on-chain: K-WOTS8-Merkle, an ML-DSA-44-like Keccak counter profile,
and a Falcon-512-like Keccak counter profile. The latter two retain their
respective lattice dimensions and norm checks, but substitute specified hash
constructions. They do not constitute standard ML-DSA or Falcon/FN-DSA.

\textbf{What changed.} The principal additions are a four-row packed ML matrix
layout, a directly packed challenge sampler, native-Keccak Falcon hash-to-point
with unbiased 32-bit draws and an eight-output common path, a base-8 hash-chain
profile, and a wallet with immutable key data and persistent one-time-key
retirement tracking. Existing lattice kernels are reused and attributed.

\textbf{What the strongest gain means.} The Falcon result is
5.73 times cheaper in total transaction gas than the particular
locally reproduced Keccak path. A newer published optimized SHAKE-based Falcon
verifier is a stronger comparison point; our custom verifier's execution gas
is approximately 50.3\% below that published figure, without an
identical-workload reproduction of that newer result.

\textbf{The cost of the ML improvement.} The expanded key costs
8,779,908 gas to deploy. Its extra cost over the local baseline's key
is recovered after approximately 33 verifications, considering key deployment
and per-verification savings alone.

\callout{\textbf{Scope of the performance claim.} The evidence establishes
specific measured wins. It does not establish that this implementation beats
every available implementation, preserves standard interoperability, or has
equivalent cryptographic assurance. The hash-based comparison has no
demonstrated universal lead. All custom profiles remain unaudited.}

\section{System, provenance, and measurement boundary}
\subsection{Authorization architecture}
An owner registers a root or an immutable expanded verification key and an
algorithm identifier. Owners sign a common transaction digest off-chain. A
relayer supplies an ordered approval set to the wallet, which verifies each
approval, checks the total threshold and optional algorithm minima, and
executes the authorized calls atomically. No external signature verdict,
signature oracle, SNARK verifier, or chain-specific PQ precompile is used.

Public-key expansion is performed offline. The authorized object is the
expanded verification key itself. Registration checks its representation and
arithmetic bounds; it does not prove derivation from a compact standard key.
This distinction is part of the design's trust boundary, not an unreported
off-chain verification shortcut.

\subsection{Two measurements, two evidence classes}
\textbf{Execution gas} is the local EVM's gross execution counter. It excludes
transaction base and calldata charges. \textbf{Transaction gas} is the signed
transaction's total gas spent, including calldata, refunds where applicable,
and the Prague calldata floor. Subtracting execution gas from transaction
gas is not a general decomposition when refunds or a floor apply.

external author-reported number consulted on 28 October 2026. Published

\section{ML-DSA-like profile: hashes and key representation}
\subsection{Preserved arithmetic and explicit hash substitution}
The selected profile retains the ML-DSA-44 core's $q=8{,}380{,}417$, polynomial
dimension 256, four matrix rows and four columns, challenge weight 39,
2,420-byte signature representation, strict $z$ norm checks, and canonical
hint parsing. Its Keccak counter profile matches the pinned ETHDilithium
variant rather than inventing a smaller lattice parameter set.

Let $K=\K$. The counter construction used for public verification hashing is
\begin{align}
 s &= K(\mathrm{input}),\\
 B_j &= K(s\parallel\operatorname{uint64}_{\rm BE}(j)),\quad j=0,1,\ldots
\end{align}
The stream concatenates $B_0,B_1,\ldots$ in byte order. The ML message input
uses $m'=\texttt{00}\parallel\texttt{00}\parallel d$, an empty-context
encoding of the wallet digest $d$. Verification reconstructs
\begin{align}
 \mu &= \CTR(\mathrm{tr}\parallel m',64),\\
 c &= \operatorname{SampleInBall}_{\CTR}(\widetilde c),\\
 \widetilde c\,' &= \CTR(\mu\parallel\operatorname{Encode}(w_1),32),
\end{align}
and requires $\widetilde c\,'=\widetilde c$ after the lattice and hint checks.
The 64-byte $\mathrm{tr}$ remains SHAKE256 of the original compact public key.
The generated reference signer changes these public message/challenge
hashes and SampleInBall; its secret-key generation, signing-mask expansion,
and matrix expansion are retained. Standard ML-DSA uses SHAKE in these
locations, so the selected profile is a distinct experimental scheme.

\subsection{Column-major storage, four rows per word}
For coefficient index $i$, precompute the packed column word
\begin{equation}
 P_j[i]=\sum_{r=0}^{3}\widehat A_{r,j}[i]\,2^{64r},\qquad j=0,1,2,3,
\end{equation}
and the corresponding packed key term
\begin{equation}
 T[i]=\sum_{r=0}^{3}\NTT(2^{13}t_{1,r})[i]\,2^{64r}.
\end{equation}
Each stored field is canonical and less than $q$. The five columns contain
$5\cdot256\cdot32=40{,}960$ bytes. They are split across two 20,480-byte
data payloads, each with a STOP byte. This keeps each deployed data runtime
below 24,576 bytes.

The descriptor payload is
\begin{equation*}
 \mathrm{part}_0[20]\parallel\mathrm{part}_1[20]\parallel\mathrm{tr}[64].
\end{equation*}
It has 104 bytes, or 105 bytes including STOP. Canonical field checks and
fixed lengths establish the bounds needed by the packed arithmetic. Content
identity is $K(\mathrm{tr}\parallel\mathrm{expandedColumns})$, so copying
the same expanded credential to another address does not create another vote.

\section{ML-DSA-like profile: matrix and challenge kernels}
\subsection{One EVM multiplication supplies four row products}
The transformed signature coefficient $\widehat z_j[i]$ is a scalar. Its
product with $P_j[i]$ computes four row products simultaneously:
\begin{equation}
 P_j[i]\widehat z_j[i]
 =\sum_{r=0}^{3}\big(\widehat A_{r,j}[i]\widehat z_j[i]\big)2^{64r}.
\end{equation}
The implementation forms the four-row raw accumulator
\begin{equation}
 R[i]=\sum_{r=0}^{3}(q2^{28})2^{64r}
       +\sum_{j=0}^{3}P_j[i]\widehat z_j[i]-T[i]\widehat c[i].
\end{equation}
The offset prevents subtraction borrow between lanes. Given the registered
key bounds and the reused transform's $\widehat z,\widehat c<17q$ bound,
each raw row coefficient lies in $[0,q2^{30})$. For example,
\begin{align*}
 q2^{28}-17q^2 &> 0,\\
 q2^{28}+68q^2 &< q2^{30}<2^{64}.
\end{align*}
Thus neither carry nor borrow changes a neighbouring row. The kernel
transposes groups of four output words into the existing inverse-NTT/hint
layout. It avoids re-unpacking the matrix on every verification.

64-bit coefficient lanes. It avoids the upstream 256-word intermediate,
per-byte PRNG helper calls, and a subsequent packing pass. Coefficient payload
storage falls from 8,192 to 2,048 bytes; these figures exclude array headers
and other memory allocations.

order, rejection of byte draws above the current position, swap/placement
semantics, challenge weight 39, and the same counter stream as the compared
Keccak profile. No challenge-norm or hint bound is removed.

\section{Falcon-like profile: sampling and norm accumulation}
\subsection{Preserved lattice verification}
The verifier retains $n=512$, $q=12{,}289$, and the squared-norm bound
$\beta^2=34{,}034{,}726$. With the point polynomial $u$ and public key $h$,
it checks
\begin{equation}
 \|\operatorname{center}(u-s_2h)\|_2^2+
 \|\operatorname{center}(s_2)\|_2^2\leq\beta^2.
\end{equation}
The eight-lane product and compact $s_2$ norm logic are reused from pinned
ETHFALCON. Verification uses integer arithmetic. The reference signer's
floating-point Gaussian sampling machinery is unchanged.

\subsection{Domain-separated native Keccak expansion}
The input to the counter construction is
\begin{equation*}
 K(\texttt{PQWALLET/FALCON512/POINT32/v1})
 \parallel\mathrm{salt}[40]\parallel d[32].
\end{equation*}
This replaces the SHAKE-based point derivation and changes the scheme's
interoperability. It removes software SHAKE permutations from the custom
verification path. The EVM's Keccak256 opcode is not a drop-in SHAKE opcode.

\subsection{32-bit unbiased draws, eight candidates per word}
Interpret successive four-byte stream segments as big-endian uint32 values.
With
\begin{equation}
 L=\left\lfloor\frac{2^{32}}q\right\rfloor q=4{,}294{,}956{,}344,
\end{equation}
reject $x\geq L$ and map accepted $x$ to $x\bmod q$. Every residue then has
the same number of preimages in the accepted range. Unconditional modulo
would introduce bias. The rejection probability per draw is
$(2^{32}-L)/2^{32}=10{,}952/2^{32}$.

On the common path, the output index is eight-aligned, eight outputs remain,
and a bit-run detector establishes that no candidate has an all-ones upper
16-bit half. This implies each candidate is below
$\texttt{0xffff0000}<L$. One loaded product word supplies the eight
complement coefficients, and the kernel accumulates eight squared differences
without materializing a 512-element point array. Exceptional blocks perform
explicit rejection checks and bounded individual accumulation. A fixture
forces a true rejection at draw 471, exercising unaligned and tail handling.

\subsection{Registered key and signature layout}
The stored key is the full ordinary NTT of $h$ expected by the pinned kernel,
with sixteen canonical 16-bit residues per 256-bit word. Its 1,024-byte
payload is stored in STOP-prefixed code; the signature is a 40-byte salt plus
1,024 bytes of identically packed $s_2$. This is a separate wire format from
the round-3 compressed signature. It saves repeated public-key transmission
while trading a larger signature payload for inexpensive decoding.

\section{Hash-based profile: chains, checksum, and state}
\subsection{Base-8 chains rather than the base-16 comparison}
K-WOTS8-Merkle uses 32-byte chain elements, 86 message digits, four checksum
digits, and 90 chains of seven steps. For digest integer $D$,
\begin{align}
 d_i &= (D\gg(255-3i))\mathbin{\&}7,\quad i=0,\ldots,85,\\
 S &= \sum_{i=0}^{85}(7-d_i).
\end{align}
The 258-bit base-8 representation has two leading zero bits. The four
checksum digits are the high-to-low three-bit fields of $S$. The first
message digit consequently carries one message bit, not three.

Each step uses an addressed 128-byte Keccak input:
\begin{equation*}
 K(\mathrm{CHAIN}\parallel\mathrm{publicSeed}\parallel
   ((\ell\ll32)\mathbin{|}(i\ll8)\mathbin{|}j)\parallel x).
\end{equation*}
Here $\ell$ is the leaf index, $i$ the chain index, and $j$ the step. Leaf
compression binds the public seed, leaf index, and all chain endpoints.
Parent hashing binds the level and ordered children. Domains are distinct
hashes of the corresponding protocol-role strings.

The shorter chains save hashes but increase calldata. Base 8 wins this local
height-3 transaction sample by 3.8\%. Taller proofs, signature
values, calldata-floor effects, and network pricing can change the preferred
choice. No universal base-8 optimum is claimed.

\subsection{One-time-key lifecycle}
The wire layout is
\begin{equation*}
 \operatorname{uint32}_{\rm BE}(\ell)\parallel\mathrm{publicSeed}[32]
 \parallel\mathrm{chains}[2880]\parallel\mathrm{siblings}[32H],
\end{equation*}
with $0\leq H\leq20$ and $\ell<2^H$. The benchmark has $H=3$, hence only
eight leaves per root. A height-16 instance would carry 3,428 signature bytes
and support 65,536 leaf indices; no complete height-16 workload is benchmarked.

The wallet remembers a root's monotone next-leaf index across removal and
re-registration. The CLI separately locks, persists, fsyncs, and atomically
commits leaf allocation before releasing a signature. Failed transactions,
abandoned proposals, and crashes can burn off-chain leaves. An on-chain
rejection cannot repair two different signatures already disclosed under one
leaf. Independent state-file copies and rollback from backups remain unsafe.

This addressed-chain construction preserves a checksum but does not implement
WOTS+ masking or standard XMSS. It needs its own cryptographic analysis.

\section{Storage, wallet, and tooling modifications}
\subsection{Immutable data instead of persistent coefficient slots}
\source{KeyData.sol} returns a STOP byte followed by public data. Canonical
lengths and prefixes are checked when accepting keys. Data can be read with
\texttt{EXTCODECOPY}; the wallet stores the compact data address or root,
rather than thousands of coefficient SSTORE slots. The two-part ML layout
respects the ordinary EIP-170 runtime limit. Key data is public and can be
shared by wallets.

\subsection{Digest binding and threshold policy}
The signed digest is
\begin{align*}
 d=K(\operatorname{ABI}(&\mathrm{DOMAIN},\mathrm{chainId},\mathrm{wallet},
 \mathrm{epoch},\\[-2pt]
 &\mathrm{nonce},\mathrm{deadline},K(\operatorname{ABI}(\mathrm{calls})))).
\end{align*}
The exact typed fields and ABI encoding are supplied by the contract's
\texttt{digest} method. The epoch increments on each approved configuration
change, invalidating pending authorizations under older owner/policy sets.

\begin{tabularx}{\linewidth}{P{0.29\linewidth}Y}
\toprule
\textbf{Modification} & \textbf{Resulting behavior}\\
\midrule
Ordered owner IDs & Strictly increasing IDs prevent duplicate counting.\\
Content-based key identity & Equivalent credentials at different data addresses cannot receive extra votes.\\
Threshold and algorithm minima & Policies can require a total count plus hash/ML/Falcon minimum counts.\\
Single execution transaction & No per-proposal or per-approval storage transactions.\\
Transient guard & Cancun transient storage blocks reentry into execution.\\

No ECDSA owner override, unrestricted delegatecall, or administrative upgrade
key is added. Relayer identity is not spending authority. EVM call success
does not interpret token-specific returned booleans. The wallet does not
extend post-quantum security to chain consensus or the relayer's own assets.

\subsection{Signer, build, and benchmark tooling}
Reference signer adaptations are generated from pinned noble sources with
explicit source-anchor checks and retained license notices. Private key
files use exclusive creation and mode 0600; public expanded keys are exported
separately. The low-level WOTS fixture helper is distinct from persistent
allocation in the CLI. The build enforces runtime code size, records hashes
of compiled Solidity inputs, and rejects stale build artifacts before tests.
Benchmarks execute signed local transactions and validate acceptance before
recording results. The report generator reads the recorded JSON snapshot.

\section{Validation, rejected experiments, and remaining work}
\subsection{Recorded checks}
The local integration run records 37,052 assertions. Many are individual
coefficient comparisons; this is not a count of distinct signatures or
independent security experiments. The suite checks multiple messages,
malformed encodings, signature and public-key coefficient bounds, and the
exceptional Falcon rejection path.

Wallet cases cover replay, cross-wallet binding, expired authorization,
duplicate or unordered approvals, insufficient algorithm minima, altered
signatures, duplicate key contents at distinct addresses, authorized
configuration changes, root removal/re-addition, failed-batch rollback, and
reentry rejection. CLI tests cover private-file permissions, persistent leaf
allocation, concurrent processes, lock contention, and leaf exhaustion.

The arithmetic research model separately exercises 253 scalar transform
cases, 100 raw-accumulator inverses, and 10,000 five-lane Montgomery operations.
Generated code and twiddle tables are checked for reproducibility. Source
freshness checks and actual deployments enforce the configured code-size
boundary.

\subsection{Experiments deliberately excluded from the selected verifier}
The first compact transposed ML key layout was correct and reduced deployed
code, but did not produce enough verification savings. A subsequent design
packed five forward polynomials in 51-bit lanes with Montgomery
$R=2^{26}$, using the unusually small correction constant 8,380,415. It paired
this with four inverse polynomials in 64-bit lanes and generated fused
radix-8/8/4 schedules.

These transforms passed scalar comparisons but lost gas to conversion and
compiler stack traffic. They remain isolated research artifacts. The selected
ML verifier uses the existing fused NTT kernels and the expanded four-row
matrix layout. Correctness alone was not used to justify a slower replacement.

\subsection{Evidence required for stronger claims}
\begin{enumerate}
\item Independently analyze the custom hash constructions, chain construction,
and cross-domain interactions; do not transfer NIST security categories by
parameter resemblance alone.
\item Normalize compiler, fork, ABI framing, public-key preparation, memory
warmth, message length, security parameters, and setup accounting across
the newest comparable sources.
\item Measure many keys and signatures and report distributions, rejection
tails, invalid-input costs, and worst-case bounds where established.
\item Compare hash profiles at equal tree capacity and complete lifecycle
cost, including signing-state recovery and key generation.
\item Review actual deployed bytecode, wallet configuration paths, persistent
signing state, and operational integrations independently.
\end{enumerate}
No audit, cryptographic security proof, public funded deployment, or exhaustive
implementation survey has been completed for this project. Keeping lattice
bounds unchanged establishes neither hash-profile equivalence nor a
standard-compliant verifier.
